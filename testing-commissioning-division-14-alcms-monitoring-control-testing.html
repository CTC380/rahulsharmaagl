Monitoring, Control & ALCMS Testing

Divisions 01–13 qualify the individual pieces of AGL equipment. Division 14 verifies that all of it comes together as one integrated system through the Airfield Lighting Control and Monitoring System — HMI, PLC, SCADA interfaces, CCR communication, remote monitoring, remote control, alarms, status feedback, interlocks, switching logic, and event recording. This is the system-integration commissioning division: the point at which individual equipment acceptance becomes airport-wide operational control and monitoring capability.

Philosophy: ALCMS commissioning is not demonstrated by a working HMI screen alone. Every function is verified as a complete, closed-loop chain — Operator Command → HMI/SCADA → PLC → Communication Network → CCR → AGL Circuit → Field Equipment → Status Feedback → HMI/SCADA — and the equivalent reverse chain for monitoring, alarms and events.

Chain of Acceptance

ALCMS is evaluated as a complete, closed-loop chain — every link has to hold, in both the control direction and the monitoring direction, before the system is accepted.

LinkWhat It Confirms
Installation VerifiedALCMS panels, HMI, PLC, network and control wiring match the approved architecture
HMI/PLC/SCADA FunctionalDisplayed data, logic execution and integrated interfaces reflect actual field equipment
CCR Communication VerifiedEach CCR is individually addressed — a command to one CCR never operates another
Remote Monitoring VerifiedPhysical equipment condition matches HMI/SCADA indication under observed conditions
Remote Control VerifiedThe intended equipment responds; unintended equipment remains unaffected
Status Feedback VerifiedDisplayed status equals actual field condition, never assumed from the HMI alone
Interlocks & Logic VerifiedProhibited/conflicting commands are blocked; switching logic executes correctly
Alarms & Logging VerifiedAlarms, alarm history and event log correctly capture real system activity
Failure & Emergency Response VerifiedCommunication-failure and emergency conditions produce the approved system behaviour
ALCMS AcceptedAll applicable results are recorded, punch points closed, and the system formally accepted

Before Testing Begins

Two conditions should be established before ALCMS functional testing begins.

Control Philosophy Governs Everything

  • Approved control and emergency philosophy documents define expected behaviour — never assume a "sensible" response
  • Interlock testing is performed only under approved test conditions and must never defeat a safety function merely to demonstrate it
  • Communication-failure testing that could affect operational lighting is coordinated with ATC/operations beforehand
  • Emergency-control testing confirms exact conformance to the defined philosophy, not merely that "something" happens

Division Boundary

  • Divisions 01–13 verify individual AGL equipment (CCRs, transformers, cabling, fixtures, etc.)
  • Division 14 verifies the integrated system that monitors and controls that equipment
  • A displayed HMI status is never accepted as proof of a field condition — it must be cross-checked against the physical equipment
  • No ALCMS function is accepted until the full command/monitoring chain has been demonstrated end to end

The 20 Topics

Grouped by commissioning focus, in the order the ALCMS is normally worked through — click any topic to expand its verification checks and acceptance criteria.

A — ALCMS System Verification B — Communication & Monitoring C — Control & Logic D — Recording & Fault Response E — System Acceptance
A

ALCMS System Verification

4 topics
TC-ALCMS-001ALCMS Installation Verification
Verification Checks
  • Verify ALCMS panel/cabinet, HMI, PLC, communication and network equipment installation
  • Verify power supply, control wiring, communication wiring, and panel earthing
  • Verify terminal, I/O and equipment identification, plus interface connections
  • Verify environmental condition of the installation
  • Cross-check: approved ALCMS architecture → panel drawings → I/O schedule → communication architecture → physical installation
  • Check for missing/incorrect equipment, incorrect wiring, unidentified cables, loose terminals, damage, or incorrect network connection
Hold Point

Hold Point: the physical installation must fully correspond with the approved design and control architecture before functional testing proceeds.

TC-ALCMS-002HMI Verification
Verification Checks
  • Verify HMI installation and screen configuration
  • Verify equipment list, equipment status, CCR status, circuit status and intensity levels
  • Verify alarm display, control commands, navigation, indications, and date/time
  • Confirm every displayed item corresponds to the actual field equipment and approved control philosophy
  • Verify the chain: HMI indication → PLC/SCADA data → field equipment
Acceptance / Record

Acceptance Criteria: every HMI screen, indication and control accurately reflects real field equipment and status — not merely that the screen is operational.

TC-ALCMS-003PLC Verification
Verification Checks
  • Verify PLC installation, CPU, power supply, input/output and communication modules
  • Verify I/O identification, PLC status, program/configuration and communication status
  • Test the I/O chain where applicable: field input → PLC input → logic → PLC output → field equipment
  • Check for incorrect I/O mapping, missing I/O, incorrect signal, wrong equipment association, or communication fault
Hold Point

Hold Point: any incorrect I/O mapping or wrong equipment association is corrected and retested before the PLC is accepted.

TC-ALCMS-004SCADA Integration Testing
Verification Checks
  • Verify communication, equipment status, control commands, alarms and events where SCADA is provided
  • Verify intensity information, fault information and communication status
  • Test both directions: AGLCMS/PLC → SCADA, and SCADA → ALCMS/PLC → field equipment
  • Confirm displayed information is correct, timely, correctly associated with equipment, and consistent with actual field condition
Acceptance / Record

Acceptance Criteria: SCADA integration is verified where provided — data flows correctly and consistently in both directions.

B

Communication & Monitoring

5 topics
TC-ALCMS-005CCR Communication Testing
Verification Checks
  • Verify CCR communication link, CCR identification and communication status
  • Verify command transmission, status feedback, alarm transmission, intensity command and fault information
  • Test the sequence: ALCMS → CCR command → CCR response → CCR status → ALCMS feedback
  • Test multiple CCRs individually and confirm a command intended for one CCR does not operate another
Hold Point

Hold Point: cross-CCR command isolation must be positively demonstrated before proceeding to remote-control testing.

TC-ALCMS-006Remote-Monitoring Verification
Verification Checks
  • Monitor CCR status, CCR output condition, circuit status and equipment status
  • Monitor faults, alarms, communication status, operating mode and intensity setting where applicable
  • Compare physical equipment condition against HMI/SCADA indication
  • Create/observe approved operating conditions and confirm the monitoring system correctly reflects them
Acceptance / Record

Acceptance Criteria: field equipment can be remotely monitored with the monitored value matching the physical condition under every tested condition.

TC-ALCMS-007Remote-Control Testing
Verification Checks
  • Test ON command, OFF command, intensity command, operating mode and equipment selection
  • Test multiple equipment commands where applicable
  • Verify the sequence: operator command → HMI/SCADA → PLC → communication → CCR → AGL circuit → field equipment
  • Confirm the intended equipment responds correctly and unintended equipment remains unaffected
Hold Point

Hold Point: any unintended equipment response to a remote command is investigated and corrected before acceptance.

TC-ALCMS-008Alarm Communication Testing
Verification Checks
  • Test applicable alarms: CCR fault, CCR communication failure, circuit fault, equipment fault, power failure
  • Test control-system fault, emergency condition, communication failure and other project-defined alarms
  • Verify the chain: field fault → PLC/controller → ALCMS → HMI/SCADA → alarm indication
  • Record alarm ID, test condition, field/HMI/SCADA indication and result for each alarm
Acceptance / Record

Acceptance Criteria: every applicable alarm is transmitted correctly and promptly from field fault to HMI/SCADA indication.

TC-ALCMS-009Equipment-Status Feedback Testing
Verification Checks
  • Verify ON status, OFF status, fault status, local mode and remote mode
  • Verify communication status, CCR operating status and circuit status
  • Do not accept an indication merely because the HMI displays a status
  • Confirm displayed status equals actual field condition, in every tested case
Hold Point

Hold Point: every status feedback point is physically verified against the actual field condition, not accepted on HMI display alone.

C

Control & Logic

4 topics
TC-ALCMS-010Control-Interface Testing
Verification Checks
  • Verify applicable interfaces: HMI, SCADA, local control panel, remote control station, PLC, CCR interface, communication interface, emergency control interface
  • Verify command availability and correct equipment selection
  • Verify command execution, status feedback, alarm response and user-interface response
Acceptance / Record

Acceptance Criteria: every applicable control interface correctly selects, executes, and confirms commands on the intended equipment.

TC-ALCMS-011Interlocking Verification
Verification Checks
  • Verify applicable interlocks: local/remote, equipment selection, conflicting command, emergency, maintenance/control, runway/taxiway operational interlock where specified
  • Attempt the applicable prohibited or conflicting operation under an approved test condition
  • Verify the invalid/prohibited command is blocked, the equipment does not enter an unsafe/unintended state, and correct indication is generated
  • Perform interlock testing strictly per the approved control philosophy — never defeat a safety function merely to test it
Hold Point

Hold Point: interlock testing is only performed under approved test conditions and coordination; safety functions are never bypassed for the purpose of the test.

TC-ALCMS-012Switching-Logic Verification
Verification Checks
  • Verify ON/OFF logic, sequence logic, group switching and intensity-step logic
  • Verify equipment dependency, automatic logic where applicable, manual override where applicable, and interlock logic
  • Test the chain: command → logic → output → equipment → feedback
  • Check for incorrect equipment switching, delayed response, wrong sequence, unintended simultaneous operation, or missing feedback
Acceptance / Record

Acceptance Criteria: programmed switching logic executes exactly as designed, with correct sequence, timing and feedback.

TC-ALCMS-013Intensity-Command Verification
Verification Checks
  • Test each applicable intensity level through the chain: HMI/SCADA command → PLC/controller → CCR → series circuit → AGL fixtures
  • Verify correct intensity command, correct CCR response and correct step selection
  • Verify correct field response, correct HMI indication and correct status feedback
  • Record CCR/circuit, commanded step, actual step, field response, feedback and result
Acceptance / Record

Acceptance Criteria: every commanded intensity step is correctly transmitted, applied at the CCR, and confirmed both in the field and on the HMI.

D

Recording & Fault Response

5 topics
TC-ALCMS-014Alarm-History Verification
Verification Checks
  • Verify alarm generation, timestamp, equipment identification, description and status
  • Verify acknowledgement, clearance and historical record
  • Test the sequence: generate approved alarm → record → acknowledge → clear → verify history
  • Confirm the recorded alarm corresponds to the actual equipment and event
Acceptance / Record

Acceptance Criteria: the alarm history provides a complete, accurate and traceable record of every generated alarm.

TC-ALCMS-015Event-Log Verification
Verification Checks
  • Verify events including operator login, control command, equipment switching, intensity change
  • Verify alarm occurrence, acknowledgement, clearance, communication failure, system restart and mode change
  • Confirm correct event recording, timestamp, equipment, description, operator/user where applicable, and sequence
Acceptance / Record

Acceptance Criteria: the event log provides a reliable, chronologically correct record of all significant control-system activity.

TC-ALCMS-016Communication-Failure Testing
Verification Checks
  • Test applicable paths: PLC↔HMI, PLC↔SCADA, PLC↔CCR, network communication and remote control communication
  • Verify communication failure is detected, an alarm is generated, and correct status is displayed
  • Verify equipment response follows the approved philosophy, and recovery occurs correctly after restoration
  • Test the sequence: normal communication → controlled interruption → fault detection → alarm → safe/approved behaviour → restoration → recovery
Hold Point

Hold Point: communication-failure testing that could affect operational lighting is performed only with ATC/operations coordination.

TC-ALCMS-017Emergency-Control Testing
Verification Checks
  • Verify applicable functions: emergency switching, emergency stop/control, backup control, emergency lighting control
  • Verify local emergency operation, fail-safe behaviour and emergency status indication
  • Test the chain: emergency command/condition → control system → CCR/field equipment → status feedback
  • Confirm emergency operation performs exactly as defined in the approved emergency/control philosophy
Hold Point

Hold Point: any deviation from the defined emergency/control philosophy is treated as a critical non-conformance.

TC-ALCMS-018Local/Remote Control Verification
Verification Checks
  • In local mode, verify local command, local indication, remote command restriction where applicable, and correct status feedback
  • In remote mode, verify remote command, remote indication, local command behaviour per approved philosophy, and status feedback
  • Perform the mode-transfer test: LOCAL → REMOTE → verify → REMOTE → LOCAL → verify
  • Confirm the control system clearly indicates which control mode is active at all times
Acceptance / Record

Acceptance Criteria: local and remote modes each behave correctly per the approved philosophy, and the active mode is always unambiguously indicated.

E

System Acceptance

2 topics
TC-ALCMS-019ALCMS Functional Acceptance
Verification Checks
  • Confirm installation, HMI, PLC, communication equipment, control wiring and network are all verified
  • Confirm CCR communication, SCADA integration, remote monitoring and communication-failure response are verified
  • Confirm remote control, local control, control interface, switching logic, intensity commands and interlocks are verified
  • Confirm equipment-status feedback, alarm communication, alarm history and event log are verified
  • Confirm emergency control, fail-safe/approved response and recovery are verified
  • Confirm punch-list closed, retesting completed, and documentation completed
Acceptance / Record

Acceptance Criteria: ALCMS Functional Acceptance = Installation + HMI + PLC + SCADA + Communication + Monitoring + Control + Feedback + Alarms + Interlocks + Switching Logic + Intensity Commands + Event Logging + Communication-Failure Response + Emergency Control + Local/Remote Operation → ALCMS Accepted.

TC-ALCMS-020ALCMS Commissioning Report
Verification Checks
  • Record project information: airport, project, ALCMS system, control room, test date, contractor, system integrator, test engineer, client/consultant
  • Document system architecture: HMI → PLC → network → CCR → AGL circuits → field equipment, and applicable SCADA integration
  • Compile equipment schedule (HMI, PLC, CCR, SCADA) with ID, location, communication, control, monitoring and result
  • Compile control, alarm, communication, interlock and event-log test records
  • Record final acceptance status: PASS, FAIL, RETEST REQUIRED, or CONDITIONAL ACCEPTANCE
  • Obtain sign-off: tested by, checked by, contractor representative, client/consultant representative, date
Acceptance / Record

Acceptance Criteria: a dedicated, traceable ALCMS Commissioning Report is completed and signed off — this closes Division 14 and confirms the airport-wide monitoring and control environment is operational.

Division 14 runs as a single continuous system-integration sequence, from installation through to functional acceptance and the commissioning report.

2

Verify HMI displays and PLC hardware/I/O against field equipment.

3
SCADA Integration

Verify bidirectional SCADA data flow where provided.

4
CCR Communication

Verify individually addressed communication with each CCR.

5
Remote Monitoring

Confirm monitored values match physical equipment condition.

6

Confirm intended-equipment response, no unintended operation.

7

8

Verify interlocks, switching logic and intensity commands.

9
Alarm History & Events

Verify alarm history and event-log recording accuracy.

Failure & Emergency Response

Verify communication-failure and emergency-control behaviour.

11
Local/Remote Modes

Verify mode transfer and unambiguous active-mode indication.

12
Functional Acceptance & Report

Close punch-list, complete acceptance and the commissioning report.
