ALC-471 ALCMS Not Starting

Symptom — The ALCMS server/workstation application fails to start or complete its boot sequence after a restart, power cycle, or scheduled maintenance.

Equipment / System

ALCMS server/workstation — the central software application (client/server) running on redundant servers/workstations in the ATC tower or airport operations building, providing the operator interface for lighting control and monitoring.

Possible Causes
HighOS or a critical application service failing to start after a restart or power cycle
HighDatabase service (SQL Server/Oracle or equivalent) not starting, blocking the application from initialising
MedSoftware licence or dongle/licence-server unreachable at startup
MedCorrupted application configuration file preventing a clean startup
LowServer hardware fault (disk, RAM, power supply)
LowAntivirus or an OS update conflicting with the ALCMS service
Required Tools
Server console/KVM accessOS event log viewerALCMS application/service logsDatabase administration toolLicence server diagnostic utilitySpare server/workstation hardware
Safety Precautions
  • Coordinate with ATC before restarting the primary ALCMS server, since lighting control may need to fail over to a backup system or local manual control.
  • Follow the site change-management procedure for any server-level intervention.
Diagnostic Procedure
  1. ObservationCheck the server power and OS boot status to confirm whether the hardware/OS layer started correctly.
  2. ObservationReview the OS and application event logs for the specific point of startup failure.
  3. MeasurementConfirm the database service status independently of the ALCMS application.
  4. MeasurementCheck licence server or dongle connectivity if the application reports a licensing error.
  5. DecisionOS/hardware boots correctly but the application service fails → database or configuration fault. OS itself fails to boot → hardware fault.
  6. Fault LocationIsolate to the OS/hardware layer, the database service, the licence system, or a corrupted configuration file.
  7. Root CauseConfirm the specific failed component or file before restoring service.
Test Points
OS boot status
Database service status
Licence server connectivity
Application configuration file integrity
Root Cause Verification

Confirm ALCMS starts cleanly, all expected services report running, and the operator interface displays current field status correctly for a sample of monitored devices.

Corrective Action
  • Restart or repair the failed OS or database service.
  • Restore the application configuration from a known-good backup.
  • Repair or replace failed server hardware.
  • Renew or reconnect the software licence.
Preventive Action
  • Maintain a tested backup/standby ALCMS server with automatic or documented manual failover.
  • Schedule regular configuration backups.
  • Keep OS and database patching current within a controlled maintenance window.

ALC-472 ALCMS Communication Failure

Symptom — ALCMS loses communication with the field PLC/RTU network broadly, affecting visibility and control of multiple CCRs or field devices simultaneously.

Equipment / System

Overall ALCMS communication path linking the ALCMS server to the field PLC/RTU network, which in turn communicates with individual CCRs and field devices.

Possible Causes
HighNetwork switch or router failure on the path between ALCMS and the field network
HighServer-side communication service or driver fault
MedProtocol converter or gateway failure
MedA misconfigured IP address/subnet following a network change
LowA widespread cable or fibre cut affecting the whole field network
LowServer-side firewall or security policy change blocking the communication port
Required Tools
ALCMS system log reviewNetwork diagnostic tools (ping/traceroute)Protocol analyserServer communication service diagnosticsNetwork architecture drawing
Safety Precautions
  • Coordinate with ATC — a full communication loss typically requires falling back to local manual CCR control per the documented fallback procedure.
Diagnostic Procedure
  1. ObservationConfirm the scope of the failure from ALCMS — a single field device, a segment, or the entire network.
  2. MeasurementCheck the server-side communication service status.
  3. MeasurementPing/test the network path to a representative sample of field devices.
  4. MeasurementCheck network switch/router status along the path.
  5. DecisionOnly a segment affected → isolate to that segment's switch/cable. Entire network affected → server-side service or core network fault.
  6. Fault LocationIsolate to the server communication service, a network switch/router, a protocol gateway, or a widespread cable fault.
  7. Root CauseConfirm the specific failed component before restoring communication.
Test Points
Server communication service status
Network path continuity to field devices
Network switch/router status
Protocol gateway diagnostics
Root Cause Verification

Confirm ALCMS re-establishes communication with all field devices, and cross-check reported status against a physical inspection for a sample of devices.

Corrective Action
  • Restart the server communication service.
  • Replace failed network hardware.
  • Correct IP/network configuration.
  • Repair the identified cable/fibre fault.
Preventive Action
  • Implement redundant communication paths where practical.
  • Monitor network health proactively with management tools.
  • Maintain accurate network documentation and change records.

ALC-473 CCR Not Visible on ALCMS

Symptom — A specific CCR that should be reporting to ALCMS no longer appears, or appears with no data, while other CCRs continue reporting normally.

Equipment / System

An individual CCR's representation/tag within the ALCMS system — the specific point/device address that should report that CCR's status.

Possible Causes
HighThat CCR's RTU/PLC communication module has failed or lost power
MedThe CCR's device address/point configuration has been removed or corrupted in the ALCMS database
MedA local communication segment (e.g. a sub-network from a field cabinet) is down, affecting this CCR and others on the same segment
LowA physical comm cable/fibre fault specific to that CCR's connection
LowThe CCR was intentionally powered down or isolated for maintenance without updating ALCMS
Required Tools
ALCMS diagnostic terminalField RTU/PLC diagnostic toolTrue-RMS multimeterCable testerCCR-to-ALCMS point configuration list
Safety Precautions
  • Coordinate access to the CCR cabinet.
  • LOTO before any RTU/communication module work.
Diagnostic Procedure
  1. ObservationConfirm whether other CCRs on the same communication segment are also missing (segment-level) or only this one (device-level).
  2. MeasurementCheck the RTU/PLC communication module at the CCR for power and status.
  3. ObservationVerify the device address/point configuration in ALCMS matches the CCR's actual field address.
  4. MeasurementInspect the local cable/fibre connection for that CCR.
  5. DecisionOther CCRs on the segment also missing → segment-level fault, route to ALC-483/485/486. Only this CCR affected → device-level fault.
  6. Fault LocationIsolate to the RTU/PLC comm module, the ALCMS point configuration, or the local cable/fibre connection.
  7. Root CauseConfirm the specific cause before restoring visibility.
Test Points
RTU/PLC comm module status at the CCR
ALCMS point configuration
Local segment communication status
Cable/fibre continuity
Root Cause Verification

Confirm the CCR reappears on ALCMS with correct real-time status matching its actual field state.

Corrective Action
  • Restore power to or repair the RTU/PLC comm module.
  • Correct the ALCMS point configuration.
  • Repair the identified local cable/fibre fault.
  • Confirm and document the CCR's state if it had been intentionally isolated.
Preventive Action
  • Maintain an accurate CCR-to-ALCMS point configuration list.
  • Include RTU/PLC health checks in the periodic maintenance cycle.
  • Update ALCMS promptly whenever a CCR is taken out of service.

Rev 0 — Initial issue
ALC-474 Wrong CCR Status

Symptom — ALCMS displays a CCR status (ON/OFF or fault) that does not match the CCR's actual physical state, confirmed by field inspection.

Equipment / System

CCR status feedback point on ALCMS — the ON/OFF or fault status displayed for a specific CCR, sourced from a status sensor or contact at the CCR.

Possible Causes
HighStatus feedback sensor/contact at the CCR reporting incorrectly (stuck relay, miswired feedback)
MedALCMS point configured against the wrong CCR (a mapping error)
MedA stale/latched status not updating after the actual field state changed
LowA communication delay causing a temporarily stale display
LowA genuine intermittent fault at the CCR being masked by an apparently incorrect status
Required Tools
True-RMS multimeterALCMS diagnostic terminalCCR feedback wiring diagramDirect physical CCR inspection
Safety Precautions
  • Coordinate access to the CCR cabinet.
  • LOTO before feedback wiring work.
Diagnostic Procedure
  1. ObservationPhysically verify the actual CCR status against what ALCMS displays.
  2. MeasurementCheck the feedback sensor/contact wiring at the CCR.
  3. ObservationConfirm the ALCMS point mapping is assigned to the correct CCR.
  4. ObservationObserve over a short period to check whether the discrepancy is a communication delay rather than a hard fault.
  5. DecisionPhysical state and feedback wiring correct but ALCMS shows a different CCR's status → mapping error. Feedback wiring itself faulty → repair at the CCR.
  6. Fault LocationIsolate to the feedback sensor/contact, the ALCMS point mapping, or a communication delay.
  7. Root CauseConfirm the specific cause before correction.
Test Points
Physical CCR status
Feedback sensor/contact continuity
ALCMS point mapping
Communication update latency
Root Cause Verification

Change the CCR's actual state under a controlled test and confirm ALCMS updates correctly and promptly.

Corrective Action
  • Repair or replace the feedback sensor/contact.
  • Correct the ALCMS point mapping.
  • Address the communication delay if it is source-side.
Preventive Action
  • Verify feedback wiring and point mapping during commissioning and after any CCR replacement.
  • Include status accuracy spot-checks in the periodic maintenance cycle.

ALC-475 Wrong CCR Current Display

Symptom — The output current value displayed on ALCMS for a specific circuit does not match a reference measurement taken directly at the CCR.

Equipment / System

CCR output current value displayed on ALCMS for a specific circuit, sourced from a current transducer (CT) at the CCR and reported through the RTU/PLC analog input.

Possible Causes
HighCurrent transducer (CT) at the CCR faulted or drifted out of calibration
HighAnalog signal wiring fault between the CT and the RTU/PLC analog input
MedIncorrect scaling/calibration configured in the ALCMS point (engineering units mismatch)
MedAnalog input module fault on the RTU/PLC
LowElectrical noise or interference on the analog signal wiring producing an unstable reading
Required Tools
Calibrated clamp-on ammeter (reference measurement)True-RMS multimeterCT calibration/test equipmentRTU/PLC analog input diagnostic toolALCMS point scaling configuration
Safety Precautions
  • LOTO before CT or wiring work.
  • Treat CT secondary circuits with care per applicable practice — do not open-circuit an energised current transformer secondary.
Diagnostic Procedure
  1. MeasurementTake a reference current measurement directly at the CCR with a calibrated clamp-on ammeter.
  2. ObservationCompare the reference measurement against the ALCMS displayed value.
  3. MeasurementCheck the CT and its wiring to the RTU/PLC analog input.
  4. ObservationVerify the ALCMS point scaling/calibration configuration.
  5. DecisionReference measurement and ALCMS display disagree with CT/wiring confirmed sound → scaling/configuration fault. CT itself out of calibration or wiring faulty → repair at the CCR.
  6. Fault LocationIsolate to the CT, the analog signal wiring, the analog input module, or the ALCMS point scaling.
  7. Root CauseConfirm the specific cause across a range of operating currents before correction.
Test Points
Reference clamp-on ammeter reading
CT output signal
Analog input module reading
ALCMS point scaling configuration
Root Cause Verification

Confirm the ALCMS displayed current matches a reference measurement across the operating range and at each intensity step.

Corrective Action
  • Replace or recalibrate the CT.
  • Repair the analog signal wiring.
  • Correct the ALCMS point scaling configuration.
  • Replace a faulted analog input module.
Preventive Action
  • Include CT calibration verification in the periodic maintenance cycle.
  • Shield and route analog signal wiring away from sources of interference.
  • Verify scaling configuration after any RTU/PLC replacement.

ALC-477 Remote Command Failure

Symptom — A command issued from the ALCMS operator interface to a CCR or lighting circuit is not correctly executed in the field, without being specific to a step-change or ON/OFF command.

Equipment / System

General remote command path from the ALCMS operator interface to a CCR or lighting circuit — command generation, transmission, and CCR-side execution.

Possible Causes
HighCommunication path failure between ALCMS and the target field device
HighThe CCR-side controller not accepting or executing the command
MedThe operator interface command not generated correctly
MedA command queue conflict from simultaneous operator/ATC input
LowA permission or interlock condition legitimately preventing the command from executing
Required Tools
ALCMS system log reviewNetwork diagnostic toolsRTU/PLC diagnostic softwareCCR local control panel
Safety Precautions
  • Coordinate with ATC before testing remote commands.
  • Confirm local manual control is available as a fallback before extended testing.
Diagnostic Procedure
  1. ObservationConfirm the command was generated and logged correctly at ALCMS.
  2. MeasurementCheck the communication path status to the target device.
  3. MeasurementCheck the CCR's local controller for command receipt and execution.
  4. ObservationCheck for any interlock or permission condition blocking the command.
  5. DecisionCommand logged and communication path healthy but CCR does not execute → CCR-side controller fault. Command not logged at ALCMS → operator interface fault.
  6. Fault LocationIsolate to the operator interface/command generation, the communication path, the CCR local controller, or an interlock/permission condition.
  7. Root CauseConfirm the specific cause before correction.
Test Points
ALCMS command log
Communication path status
CCR local controller diagnostics
Interlock/permission status
Root Cause Verification

Issue a series of test commands and confirm each is executed correctly with accurate status feedback.

Corrective Action
  • Correct the operator interface/command generation fault.
  • Repair the communication path.
  • Repair the CCR local controller.
  • Resolve the interlock/permission conflict.
Preventive Action
  • Log and periodically review remote command success rate.
  • Verify interlock logic after any configuration change.
  • Provide clear operator guidance for handling command conflicts.

  4. ObservationCheck for a step limit or interlock condition preventing the requested step.

  6. Fault LocationIsolate to the CCR step controller/relay, the RTU/PLC register mapping, a step limit/interlock, or a protocol converter.

Remote ON/OFF command path — the specific function within the ALCMS remote command system for switching a circuit fully on or off.

  • Resolve a genuine interlock fault per the relevant division's procedure.
Preventive Action
  • Verify ON/OFF command mapping during commissioning.

ALC-480 Alarm Not Received

Symptom — A field condition that should have triggered an ALCMS alarm (fault, out-of-tolerance reading, communication loss) occurred, but no alarm was raised or displayed.

Equipment / System

ALCMS alarm management system — the logic and display that should generate an operator-visible alarm when a monitored field condition occurs.

Possible Causes
HighThe alarm point is not configured, or is disabled, in the ALCMS alarm database
HighThe alarm threshold/logic is set incorrectly so the actual field condition does not trigger it
MedThe alarm was generated at the field/RTU level but not transmitted or displayed due to a communication issue
MedThe alarm is suppressed by an active acknowledgement/silence setting from a previous event
LowAn ALCMS alarm server/service fault
Required Tools
ALCMS alarm configuration/database review toolALCMS system logRTU/PLC alarm logic diagnosticPhysical field condition verification
Safety Precautions
  • Treat any discovered alarm gap as a priority given its role in surfacing safety-relevant field conditions.
Diagnostic Procedure
  1. ObservationConfirm the field condition that should have triggered an alarm actually occurred, and establish its timing.
  2. ObservationCheck the alarm point configuration and threshold/logic in ALCMS.
  3. MeasurementCheck whether the alarm was generated at the RTU/PLC but not transmitted to ALCMS.
  4. ObservationCheck for an active suppression/silence setting on that alarm point.
  5. DecisionAlarm generated at RTU/PLC but not received → transmission/communication fault. Alarm never generated → configuration/threshold fault.
  6. Fault LocationIsolate to the alarm point configuration, the threshold/logic setting, the transmission path, or a suppression setting.
  7. Root CauseConfirm the specific cause before correction.
Test Points
Alarm point configuration
Threshold/logic setting
RTU/PLC alarm generation
Alarm transmission/communication
Suppression/silence status
Root Cause Verification

Trigger a controlled test condition, or simulate the alarm point where safe to do so, and confirm it is correctly received, displayed, and logged.

Corrective Action
  • Correct the alarm point configuration or threshold.
  • Repair the transmission/communication path.
  • Clear an inappropriate suppression setting.
  • Restart or repair the ALCMS alarm service.
Preventive Action
  • Periodically audit the alarm configuration database against the actual field point list.
  • Test alarm generation end-to-end on a defined schedule.
  • Review suppression/silence usage logs.

Rev 0 — Initial issue
ALC-481 False Alarm

Symptom — ALCMS raises an alarm without a corresponding genuine field condition, confirmed by physical inspection or independent measurement.

Equipment / System

ALCMS alarm management system, in this case generating an alarm without a corresponding genuine field condition.

Possible Causes
HighAlarm threshold set too tight/sensitive for normal operating variation (e.g. current fluctuation within normal tolerance)
HighA faulty sensor/transducer at the field device generating an erroneous reading that trips the alarm
MedElectrical noise or interference on a signal or communication line intermittently triggering the alarm logic
MedA software/logic fault in the alarm evaluation
LowA genuine but transient/self-clearing condition perceived as false because it resolved before investigation
Required Tools
ALCMS alarm history/log reviewField sensor/transducer test equipmentALCMS alarm configuration toolSignal quality logger/thermal camera
Safety Precautions
  • Do not disable or widen an alarm threshold without first confirming the underlying field condition is genuinely within normal tolerance.
Diagnostic Procedure
  1. ObservationReview the alarm history log to identify the pattern and frequency of the alarm.
  2. MeasurementCorrelate the alarm timing against the actual field condition via physical inspection or independent measurement.
  3. ObservationCheck the alarm threshold/logic configuration for appropriateness.
  4. MeasurementCheck the relevant sensor/transducer and signal path for noise or drift.
  5. DecisionIndependent measurement confirms no genuine condition at alarm times → threshold too tight or sensor drift. Independent measurement confirms a genuine but transient condition → alarm is correct, review response process instead.
  6. Fault LocationIsolate to the alarm threshold/logic, the sensor/transducer, or the signal path.
  7. Root CauseConfirm the specific cause across several alarm occurrences before adjustment.
Test Points
Alarm history/log pattern
Independent field measurement at the time of alarm
Alarm threshold/logic configuration
Sensor/transducer and signal path condition
Root Cause Verification

Monitor the point over a subsequent period to confirm the alarm no longer triggers inappropriately, while still correctly triggering for a genuine test condition.

Corrective Action
  • Adjust the alarm threshold/logic to an appropriate value.
  • Repair or replace the faulty sensor/transducer.
  • Address the noise/interference source.
  • Correct the alarm evaluation logic.
Preventive Action
  • Review alarm threshold settings periodically against actual operating data.
  • Include sensor/transducer calibration in the periodic maintenance cycle.
  • Document the rationale for each alarm threshold to avoid future drift.

Case Study: Division 01 — CCR Troubleshooting

Rev 0 — Initial issue
ALC-482 Alarm Not Clearing

Symptom — An active alarm persists on the ALCMS display after the underlying field condition appears to have been resolved.

Equipment / System

ALCMS alarm management system — in this case, an active alarm that persists after the underlying field condition has been resolved.

Possible Causes
HighThe underlying field condition has not actually been fully resolved despite appearing corrected
HighA latched alarm requiring manual acknowledgement/reset that has not been performed
MedA stale communication link preventing the cleared status from being received
MedAn alarm logic fault holding the alarm active regardless of the actual condition
LowA database/software fault in the alarm server retaining the alarm state
Required Tools
ALCMS alarm management terminalPhysical field condition verification/measurementRTU/PLC alarm logic diagnosticALCMS alarm server diagnostics
Safety Precautions
  • Confirm the field condition is genuinely resolved before manually clearing/acknowledging an alarm, to avoid masking a real ongoing fault.
Diagnostic Procedure
  1. ObservationPhysically verify the underlying field condition is actually resolved.
  2. ObservationCheck whether the alarm requires manual acknowledgement/reset per its configured behaviour.
  3. MeasurementCheck communication status to confirm the cleared field status is being received.
  4. ObservationCheck the alarm logic and server for a fault retaining the state.
  5. DecisionField condition confirmed genuinely resolved and alarm configured to auto-clear → communication or logic fault. Field condition not actually resolved → investigate the underlying fault directly.
  6. Fault LocationIsolate to the required manual acknowledgement, the communication link, or the alarm logic/server.
  7. Root CauseConfirm the specific cause before clearing the alarm.
Test Points
Physical field condition
Alarm acknowledgement/reset requirement and status
Communication link status
Alarm server/logic diagnostics
Root Cause Verification

Confirm the alarm clears correctly and the alarm history log correctly timestamps the resolution.

Corrective Action

Symptom — The ALCMS-to-field communication path exhibits periodic drop-outs rather than a complete or permanent loss, with connectivity intermittently recovering on its own.

Equipment / System

ALCMS-to-field communication path generally, exhibiting periodic drop-outs rather than a complete/permanent loss.

Possible Causes
HighMarginal signal quality on a communication cable/fibre segment (partial damage, poor termination) causing intermittent drop-outs
HighA network switch/port with an intermittent hardware fault
MedElectromagnetic interference affecting a communication segment periodically (e.g. near high-power equipment)
MedA communication device (RTU/PLC/gateway) overheating or resetting intermittently
LowA network loading/congestion issue causing periodic timeouts under peak polling load
Required Tools
Network diagnostic tools (extended ping/packet loss logging)Protocol analyserCable/fibre test equipment (OTDR for fibre)Thermal imaging cameraNetwork switch port diagnostics
Safety Precautions
  • Treat intermittent communication as a developing fault requiring investigation before it becomes a complete failure.
Diagnostic Procedure
  1. ObservationReview the ALCMS communication log to establish the pattern, frequency, and any correlation with time of day, weather, or load.
  2. MeasurementTest the suspect cable/fibre segment for signal quality/loss.
  3. MeasurementCheck network switch port statistics for errors.
  4. MeasurementCheck for a communication device resetting or overheating intermittently.
  5. DecisionIntermittency correlates with load/time of day → congestion or thermal cause. Intermittency correlates with a specific segment regardless of load → cable/fibre or switch fault.
  6. Fault LocationIsolate to the cable/fibre segment, the network switch/port, an interference source, or an overheating/resetting device.
  7. Root CauseConfirm the specific cause before correction.
Test Points
Communication log pattern and correlation
Cable/fibre signal quality
Network switch port error statistics
Communication device thermal/reset behaviour

Corrective Action
  • Repair or replace the degraded cable/fibre segment.
  • Replace a faulted network switch/port.
  • Address the interference source.
  • Repair or replace an overheating/resetting communication device.
Preventive Action
  • Include periodic communication log review and packet-loss trending in the maintenance cycle.

ALC-486 Communication Cable Failure

Symptom — A specific communication cable or fibre segment within the ALCMS network is identified as faulted following investigation of a device- or segment-level communication issue.

Equipment / System

A specific communication cable or fibre segment within the ALCMS network — between a field cabinet and a PLC/RTU, or between network nodes.

Possible Causes
HighPhysical cable/fibre damage from excavation, pavement maintenance, or rodent activity
HighA degraded or improperly terminated connector/splice
MedMoisture ingress into a below-grade cable/fibre joint
MedUV or mechanical degradation of an above-ground cable run
LowA cable route exceeding the maximum specified length/attenuation for the protocol in use
LowCrosstalk or interference from routing alongside a high-power circuit
Required Tools
Cable/fibre test equipment (TDR for copper, OTDR for fibre)Continuity testerCable route as-built drawingSplice/termination toolsExcavation permit and utility locate if digging is required
Safety Precautions
  • LOTO the associated communication equipment before cable work.
  • Obtain excavation clearance and utility locates before opening pavement or ground.
  • Coordinate airside access as required.
Diagnostic Procedure
  1. ObservationIdentify the specific cable/fibre segment implicated from the network diagnostic and route drawing.
  2. MeasurementTest the segment with a TDR/OTDR to locate the fault distance and type (break, high attenuation, poor splice).
  3. ObservationPhysically inspect accessible portions of the route for damage.
  4. DecisionFault localised to a specific distance/splice → targeted repair at that point. No localised fault found but attenuation is high overall → route length/specification issue.
  5. Fault LocationIsolate to a specific point along the cable/fibre route, a splice/termination, or an overall route length/attenuation issue.
  6. Root CauseConfirm the specific cause once the fault location is exposed.
Test Points
Cable/fibre continuity and attenuation
Splice/termination quality
Physical route condition
Cable length/attenuation vs. protocol specification
Root Cause Verification

After repair, re-test the segment to confirm continuity/attenuation is within specification, and confirm communication is restored end-to-end.

Corrective Action
  • Repair or replace the damaged cable/fibre segment.
  • Re-terminate or re-splice a degraded connection.
  • Reroute a cable found too close to a high-power circuit source of interference.
Preventive Action
  • Maintain an accurate cable/fibre route as-built drawing.
  • Coordinate with civil works teams before excavation near known routes.
  • Use appropriately rated cable for below-grade or high-interference environments.
