ALCMS Database Server

The central, high‑performance data repository for the Airfield Lighting Control and Monitoring System. The ALCMS Database Server stores all configuration data, real‑time status information, historical event logs, alarm histories, and operational parameters, providing a secure, scalable, and highly available foundation for AGL system management, reporting, and analytics.

Overview

What Is It?

The ALCMS Database Server is the core data management component of the Airfield Lighting Control and Monitoring System. It is a purpose‑built database system (typically SQL or time‑series based) that serves as the single source of truth for all AGL operational data. The Database Server stores and manages everything from static configuration data (airfield layout, circuit mappings, equipment inventory) to dynamic operational data (real‑time status, alarms, event logs, and operator actions), providing the data backbone for the entire ALCMS ecosystem.

Key characteristics of the ALCMS Database Server include:

  • Centralised Data Repository: Consolidates all AGL data — configuration, real‑time status, historical events, alarms, operator logs, and maintenance records — into a single, consistent database.
  • High Availability & Redundancy: Deployed in active‑passive or active‑active clustering configurations with automatic failover, ensuring continuous data access even during server failures.
  • Scalable Performance: Optimised for high‑throughput write operations (thousands of events per second) and fast query responses (milliseconds), supporting large airfields with thousands of light fixtures and sensors.
  • Data Integrity & Security: Implements robust transaction management, ACID compliance, encryption at rest, and role‑based access control to protect sensitive operational data.
  • Comprehensive Data Model: Supports the full AGL data model — including circuits, CCRs, light fixtures, transformers, alarms, events, users, and maintenance activities — with relationships and metadata.
  • Built‑in Archiving & Retention: Includes automated data archiving and purging policies to manage storage growth while preserving historical data for regulatory compliance.
  • Integration APIs: Provides standard interfaces (SQL, ODBC, JDBC, REST API, OPC UA) for seamless integration with ALCMS workstations, SCADA systems, and enterprise asset management (EAM) platforms.

The ALCMS Database Server is typically deployed as a dedicated physical server or virtual machine in the airfield's control centre or data centre. It is the foundation upon which all ALCMS functionalities — monitoring, control, reporting, and analytics — are built. Its reliability, performance, and security are critical to the safe and efficient operation of the airfield lighting system.

Purpose

Purpose & Function

The database server's purpose is to make sure every part of the ALCMS — every workstation, every operator, every report — is working from the same set of facts. Without a single authoritative store, it becomes possible for one screen to show a fixture as healthy while another still reflects a fault that was actually cleared minutes ago, which is exactly the kind of inconsistency that erodes an operator's confidence in what they're looking at during an active event. High availability and clustering matter for the same underlying reason: this database isn't just holding data, it is effectively the system's memory of the entire airfield's lighting state and history, and losing access to it — even briefly — means losing the ability to reliably monitor, control, or later account for what happened, not just losing one server's worth of information.

Application

Where Is It Used?

The ALCMS Database Server is deployed in every airfield with a modern AGL control and monitoring system, serving as the backbone for all data‑driven operations. Key applications include:

  • ALCMS Core Infrastructure: Providing the data persistence layer for the ALCMS server, workstations, and operator consoles, ensuring that all status information, alarms, and commands are stored reliably.
  • Real‑Time Status Management: Maintaining up‑to‑date status of every circuit, CCR, light fixture, and sensor, enabling the ALCMS to display current operational states to operators.
  • Event & Alarm Logging: Storing all system events, alarm activations, and operator actions with precise timestamps, providing a complete audit trail for incident investigation and compliance.
  • Configuration Management: Storing and version‑controlling all system configurations — including circuit assignments, brightness step mappings, alarm thresholds, and user permissions.
  • Reporting & Analytics: Providing the data foundation for generating operational reports, maintenance dashboards, performance trends, and predictive analytics.
  • SCADA & Enterprise Integration: Serving as the data interface for integration with airport‑wide SCADA systems, enterprise asset management (EAM) systems, and business intelligence platforms.
  • Regulatory Compliance: Providing the data retention and audit capabilities required by FAA, ICAO, and other regulatory bodies for AGL system records.
  • Maintenance & Asset Management: Tracking maintenance history, equipment lifecycles, and repair records to support predictive and preventive maintenance programs.
Placement

Installation & Location

The database server is installed as a rack-mounted physical server or virtual machine in the airfield's main control centre or data centre, in a climate-controlled room alongside the ALCMS application server and core network equipment rather than out at any field location. Where high availability is specified, a second server is installed in a physically separate room, building, or site, connected by a dedicated replication link so that a fire, flood, or power event affecting one location cannot take down both database instances at once. Power is drawn from a UPS-protected, and ideally dual-fed, circuit, since an uncontrolled shutdown during a write operation risks database corruption rather than a mere loss of connectivity. Storage is sized and configured (RAID, SSD tiering) for the sustained high-throughput write load of continuous event logging, and the server's network connection ties into the same redundant core switching used by the rest of the ALCMS infrastructure so database access does not depend on a single network path.

Function

How Does It Work?

The ALCMS Database Server operates as a high‑performance data management engine, handling both real‑time operational data and historical records. Key functional aspects include:

  • Data Ingestion: The database receives data from multiple sources — the ALCMS server (which aggregates data from field devices), operator workstations (for configuration changes and commands), and external systems (SCADA, maintenance). Data is ingested via APIs, SQL statements, or message queues (e.g., MQTT, AMQP).
  • Data Storage & Indexing: The database stores data in optimised tables or collections. For high‑volume time‑series data (events, alarms, status changes), a time‑series database engine (e.g., TimescaleDB, InfluxDB) may be used. Indexes are created on key fields (timestamp, device ID, event type) to support fast queries.
  • Real‑Time Data Access: The database provides low‑latency access to real‑time data (current status, active alarms) via in‑memory caches or materialised views. This ensures that operators see near‑instantaneous updates on their consoles.
  • Historical Query & Retrieval: For historical analysis, the database supports complex queries with time‑range filters, aggregations, and joins across multiple tables. Query performance is optimised through partitioning (by date), compression, and summarisation (pre‑aggregated views).
  • Transaction Management: All write operations are wrapped in ACID transactions to ensure data consistency. This is critical for configuration changes and command execution, where partial updates could lead to inconsistent system states.
  • Data Security & Access Control: The database enforces role‑based access control (RBAC) at the table, row, and column levels. All access attempts are logged for security auditing. Data at rest is encrypted using industry‑standard encryption (AES‑256).
  • Backup & Recovery: Automated full and incremental backups are performed regularly. Point‑in‑time recovery capabilities allow restoration to any previous state, protecting against data corruption or accidental deletion.
  • High Availability & Failover: In critical installations, the database is deployed in a cluster with automatic failover. The active node handles all read/write operations, while the passive node replicates data and takes over seamlessly in the event of a failure.
  • Data Archiving & Retention: Configurable retention policies automatically archive or purge old data. For example, detailed event logs may be retained for 90 days, while aggregated summaries are kept for 10 years. Archived data can be moved to cheaper storage (tape, cloud) for long‑term preservation.

The Database Server is maintained by system administrators and database specialists. It is monitored continuously for performance, storage capacity, and health, with alerts generated for any anomalies. Regular maintenance tasks — such as reindexing, vacuuming, and statistics updates — are scheduled to ensure optimal performance.

Construction

Physical Construction

The database server is built in a standard 19-inch rack-mount chassis, sized to the storage capacity required (typically 2U to 4U), with front-accessible hot-swap drive bays arranged in a RAID 10 array so any single drive can fail — or multiple drives, provided no two failed drives belong to the same mirrored pair — without interrupting data availability. Dual hot-swappable power supplies at the rear are fed from independent circuits so either can be pulled and replaced without powering down the server, and high-speed NVMe SSDs are used for the active database tier while larger-capacity HDDs handle long-term archive storage within the same chassis or an attached storage shelf. Dual 10 GbE network interfaces, optionally backed by fibre SFP modules, are mounted on expansion cards secured to the chassis rail system, keeping the high-throughput data path independent of the server's management network connection. The unit is designed to sit in a temperature- and humidity-controlled server room or data-centre rack, with a lockable front bezel restricting physical access to drive bays and power controls, and where clustering is used for high availability, the standby server is installed in a physically separate rack or room so a single point of failure cannot take out both nodes.

Field Notes

Common Field Issues

Storage Capacity Exhaustion

High event volumes and long retention periods can rapidly consume storage, leading to database performance degradation or failure. Implement capacity planning with growth projections, set aggressive archiving policies, and monitor disk usage with alerts. Consider using tiered storage (SSD for hot data, HDD for warm data, cloud/tape for cold data).

Query Performance Degradation

As the database grows, complex historical queries can become slow, affecting operator productivity and reporting. Use partitioning (by date), indexing strategies, and materialised views for common queries. Regularly update statistics and reindex. Consider using a dedicated reporting database (read replica) to offload analytical queries.

Data Corruption or Loss

Hardware failures, software bugs, or power outages can cause data corruption. Implement a robust backup and recovery strategy with regular restores testing. Use RAID storage, battery‑backed cache, and transaction logging (WAL) to minimise data loss. Consider using a database with built‑in corruption detection and repair.

Replication Lag

In high‑availability clusters, replication lag between the primary and secondary nodes can cause data inconsistency during failover. Monitor replication lag and keep it below acceptable thresholds (e.g., < 1 second). Use synchronous replication for critical data and asynchronous for less critical data.

Security Breaches

Unauthorized access to the database can lead to data theft, modification, or deletion. Enforce strong authentication, role‑based access control, and encryption at rest. Audit all database access and regularly review logs. Keep the database software and operating system patched and up‑to‑date.

Backup Failures

If backups fail silently, data may be unrecoverable after a disaster. Implement automated backup validation (e.g., restore testing). Use multiple backup destinations (local, off‑site, cloud). Monitor backup job status and set up alerts for failures.

Configuration Drift

Over time, database configuration parameters may drift from optimal settings, affecting performance. Document all configuration changes and use configuration management tools (e.g., Ansible, Puppet) to maintain consistent settings across environments. Regularly review and tune parameters based on workload.

Time Synchronisation Issues

If the database server's time drifts from the system time source, event timestamps may become inconsistent. Ensure the database server is synchronized with a reliable NTP server (preferably GPS‑disciplined). Monitor time offset and set up alerts for drift > 100 ms.

Diagnostics

Troubleshooting Guide

Database Running Low on Disk Space or Performance Degrading
Likely Cause
Storage capacity exhaustion from high event volumes and long retention, or an under-tiered storage configuration.
Diagnostic Steps
Check disk usage trend against capacity alerts; review current retention and archiving policy against actual growth rate; verify tiered storage (hot/warm/cold) is functioning as designed.
Corrective Action
Trigger archiving or purge policies, expand storage capacity, and correct tiering so cold data moves off primary storage as intended.
Historical Queries or Reports Running Slowly
Likely Cause
Missing or stale indexes/statistics, lack of partitioning, or analytical queries competing with live operational load.
Diagnostic Steps
Review query execution plans for full table scans; check index and statistics maintenance schedule; confirm whether reporting queries are running against a read replica or the live primary.
Corrective Action
Rebuild indexes and update statistics, apply date-based partitioning where missing, and offload analytical/reporting queries to a dedicated read replica.
Suspected Data Corruption or Missing Records
Likely Cause
Hardware failure, an unclean shutdown/power event, or a software bug affecting the write path.
Diagnostic Steps
Check database integrity/consistency check tools; review transaction logs (WAL) around the time of the incident; correlate with any recent power events or hardware alerts.
Corrective Action
Restore the affected data from the most recent validated backup, and verify RAID, battery-backed cache, and transaction logging are functioning correctly to reduce future risk.
Failover Produces Inconsistent or Stale Data
Likely Cause
Replication lag between primary and secondary nodes exceeded the acceptable threshold at the moment of failover.
Diagnostic Steps
Check replication lag metrics leading up to the failover event; confirm whether the affected data path uses synchronous or asynchronous replication.
Corrective Action
Reconcile data discrepancies from logs where possible, and switch critical data paths to synchronous replication if asynchronous lag caused the inconsistency.
Unexpected Access or Data Changes Detected
Likely Cause
Weak authentication, excessive privilege assignment, or unpatched database/OS vulnerabilities exploited.
Diagnostic Steps
Review access logs and audit trails for the affected records; check role-based access control assignments against current authorised personnel; verify patch levels on the database and OS.
Corrective Action
Revoke or correct excessive privileges, enforce strong authentication and encryption at rest, and apply outstanding security patches.
Backup Job Reports Success But Restore Fails
Likely Cause
A silent backup failure (e.g., incomplete file, corrupted archive) that was not caught because restore testing wasn't performed.
Diagnostic Steps
Attempt a full restore of the most recent backup to a test environment; review backup job logs for warnings that may have been missed.
Corrective Action
Implement automated restore validation for every backup cycle and maintain backups across multiple destinations (local, off-site, cloud).
Timestamps Inconsistent Across Logged Events
Likely Cause
The database server's clock has drifted from the authoritative time source.
Diagnostic Steps
Check the server's NTP sync status and current time offset; confirm the NTP source is a reliable, ideally GPS-disciplined, reference.
Corrective Action
Correct NTP configuration to sync against a reliable source and set an alert threshold (e.g., > 100 ms drift) to catch future desynchronisation early.

Engineering & Expert Notes

By Rahul Sharma

Test Failover, Don't Just Configure It
Reliability

An active-passive or active-active cluster that's correctly configured on paper can still fail to fail over cleanly in practice due to replication lag, split-brain conditions, or an untested application-side reconnect path; schedule a genuine failover drill periodically rather than relying on the configuration documentation alone.

Verify Backups Are Restorable, Not Just Completing
Maintenance

A backup job that reports success every night can still be silently producing an unrestorable backup due to a schema change, a permissions issue, or corrupted media; periodically perform an actual test restore to a separate environment rather than trusting the job's completion status as proof the backup works.

Write Throughput Degrades Gradually as Historical Data Accumulates
Performance

A database sized and indexed for the expected data volume at commissioning can see query and write performance degrade gradually over years as historical tables grow, particularly if archiving or partitioning of old data wasn't built into the original design. Monitor performance trend against data volume, not just against a point-in-time benchmark.

Patch Management Needs a Defined Maintenance Window, Not an Ad-Hoc Approach
Cybersecurity

Database security patches are as important on a system this central as on any enterprise server, but applying them without a tested rollback plan on a system that everything else in the ALCMS depends on carries real operational risk; define a proper patching cadence and test procedure rather than deferring patches indefinitely to avoid disruption.

Time Synchronisation Errors Corrupt Historical Analysis Silently
Data Integrity

If the server's own clock drifts out of sync with the field devices and controllers feeding it data, timestamps recorded in the database can become subtly misleading for sequence-of-events analysis without any obvious error being logged. Verify the server's time source and synchronisation health as its own monitored item.

An ALCMS-Wide Slowdown May Trace Back to the Database, Not the Field Network
Troubleshooting

Operators reporting sluggish screen updates or delayed alarm display across the whole system often assume a field communication issue, but a database query bottleneck or a locking contention issue on the server can produce identical symptoms; check database performance metrics early in that kind of investigation, not last.

Typical maintenance tasks and intervals are: Backup & Restore Verification (quarterly); Failover Test (annual); Storage Capacity & Retention Review (quarterly); Access Control & Security Audit (annual); Replication Health Check (semi-annual); OS & Database Patching (quarterly); Hardware Health Check (semi-annual); Performance Baseline Review (quarterly). Your airport's approved maintenance programme takes precedence.

Q9How do I troubleshoot common ALCMS Database Server faults?

Common symptoms covered are: Database Running Low on Disk Space or Performance Degrading; Historical Queries or Reports Running Slowly; Suspected Data Corruption or Missing Records; Failover Produces Inconsistent or Stale Data; Unexpected Access or Data Changes Detected; Backup Job Reports Success But Restore Fails; Timestamps Inconsistent Across Logged Events. For example, for "Database Running Low on Disk Space or Performance Degrading": Likely Cause: Storage capacity exhaustion from high event volumes and long retention, or an under-tiered storage configuration. Diagnostic Steps: Check disk usage trend against capacity alerts; review current retention and archiving policy against actual growth rate; verify tiered storage (hot/warm/cold) is functioning as designed. Corrective Action: Trigger archiving or purge policies, expand storage capacity, and correct tiering so cold data moves off primary storage as intended.
