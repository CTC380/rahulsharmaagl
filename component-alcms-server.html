ALCMS Server

The central computing platform of the Airfield Lighting Control and Monitoring System (ALCMS). It aggregates data from field equipment, executes control logic, stores historical logs, manages alarm events, and provides a secure interface for operators to monitor and control all AGL assets from a single, unified dashboard.

Overview

What Is It?

The ALCMS Server (Airfield Lighting Control and Monitoring System Server) is the central computing and data management platform for the entire airfield ground lighting system. It is a high‑reliability industrial server that runs specialised software to communicate with field equipment—CCRs, remote I/O, PLCs, and smart fixtures—over various communication protocols (Ethernet, serial, fibre optic). The server provides a centralised point of control, monitoring, and data logging for all AGL assets across the airfield.

Key characteristics of the ALCMS server include:

  • High Reliability: Designed for 24/7/365 operation in critical infrastructure environments, often with redundant power supplies, RAID storage, and hot‑swappable components.
  • Industrial‑Grade Hardware: Built with industrial‑grade motherboards, processors, and memory that are tested for extended temperature ranges, vibration, and electromagnetic interference.
  • Redundancy: Typically deployed in a primary‑backup or active‑active configuration to ensure uninterrupted operation in the event of a hardware failure.
  • Secure Communication: Supports encrypted communication protocols (e.g., TLS, HTTPS) and role‑based access control (RBAC) to ensure that only authorised personnel can control or modify AGL settings.

Core functions of the ALCMS server include:

  • Data Acquisition: Polling field equipment (CCRs, remote I/O, sensors) for status, current readings, alarm states, and fault conditions.
  • Control Execution: Sending command signals to CCRs for brightness step changes, switching circuits on/off, and controlling stop bars and other field equipment.
  • Alarm Management: Processing and prioritising alarms from field equipment, displaying them on operator workstations, and logging them for historical analysis.
  • Logging and Reporting: Storing historical data on circuit status, current readings, alarm events, and operator actions for compliance, reporting, and trend analysis.
  • User Interface: Serving the operator interface (HMI/SCADA) to workstations, presenting a visual representation of the airfield with real‑time status indicators.

The server is typically installed in a secure equipment room or control tower, connected to the airfield network via redundant fibre optic or Ethernet links. It is maintained by the airfield's IT and engineering teams, with regular backups, patches, and performance monitoring.

Purpose

Purpose & Function

The ALCMS server exists as the single source of truth for the entire airfield lighting system's status, because without centralised data acquisition and control execution, every operator workstation, alarm panel, and remote HMI would need its own independent connection to hundreds of field devices — a fragile, inconsistent, and effectively unmanageable architecture. By consolidating polling, control commands, and historical logging into one authoritative platform, the server ensures every part of the AGL system sees the same, current picture of the field.

Its emphasis on redundancy and 24/7/365 reliability reflects what's actually at stake if it fails: since it's the platform that processes alarms, executes control commands, and serves the operator interface, a server outage doesn't just lose data — it can cut operators off from monitoring and controlling live runway and taxiway lighting, which is why hot-swappable components and active-active configurations are standard rather than optional for this role.

Application

Where Is It Used?

The ALCMS server is used in all airfields that have a modern AGL control and monitoring system, including:

  • International Airports: Managing large‑scale AGL systems with multiple runways, taxiways, and approach lighting systems, often with redundant servers and distributed I/O.
  • Regional Airports: Providing centralised control and monitoring for smaller but still critical AGL systems, often with a single server and a limited number of workstations.
  • Military Air Bases: Supporting mission‑critical AGL operations with enhanced security features and redundant configurations.
  • Heliports: Controlling and monitoring heliport lighting systems, often with a smaller‑scale ALCMS server.
  • Airfield Equipment Shelters: The server may be installed in an airfield equipment shelter near the CCR room, or in the control tower, depending on the architecture.

The server is the core component of the ALCMS architecture, which typically includes:

  • Field Equipment: CCRs, remote I/O modules, PLCs, smart transformers, and sensors.
  • Communication Network: Fibre optic backbone, Ethernet switches, and communication gateways.
  • Operator Workstations: Desktop PCs or thin clients running the ALCMS operator interface.
  • Peripheral Systems: Printers for alarm logging, external displays for status boards, and integration with other airport systems (e.g., ATC, ground handling).

The server is typically specified with high‑availability features, including dual power supplies, RAID 1 or RAID 10 storage, and redundant network interfaces. The software is designed to be fault‑tolerant, with automatic failover to a backup server in the event of a primary server failure.

Placement

Installation & Location

Servers are rack-mounted in the airport's main equipment room or a dedicated ALCMS server room with controlled access, conditioned power (UPS-backed), and adequate cooling for continuous operation, rather than in the operator-facing control room itself. Where the system is configured with redundant servers, the pair is split across separate racks or rooms on independent power feeds so a single electrical or physical fault cannot take down both; network cabling runs to the site's core switches on structured cabling rather than field cable, keeping the server room's cabling entirely separate from the field-device wiring that terminates at PLCs and Remote I/O out at the substations.

Function

How Does It Work?

The ALCMS server functions as the central brain of the airfield lighting system, orchestrating all control, monitoring, and data management activities:

  • Communication Engine: The server runs a communication engine that polls field equipment at configurable intervals (typically 1‑5 seconds). It uses protocols such as IEC 61850, MODBUS, DNP3, or proprietary protocols to communicate with CCRs, remote I/O, and smart fixtures. The engine handles time‑stamping, retries, and error handling to ensure reliable data exchange.
  • Database Management: The server hosts a real‑time database that maintains the current state of all AGL equipment (on/off status, current level, alarm states). This database is continuously updated and serves as the source of truth for operator displays. Historical data is logged to a separate historian database for analysis and reporting.
  • Alarm Processing: The server analyses incoming data for abnormal conditions, such as circuit faults, overcurrent, undercurrent, or communication loss. Alarms are categorised by severity (critical, major, minor) and displayed on operator workstations with clear visual and audible indicators. The server also logs all alarm events for later review.
  • Command Execution: When an operator initiates a control action (e.g., changing brightness level, turning on a runway), the server validates the command (checking permissions, operational constraints), formats it into the appropriate protocol, and transmits it to the target field device. The server then confirms the successful execution and updates the operator interface.
  • User Interface: The server hosts a web‑based or client‑server graphical user interface that is accessed by operator workstations. The interface provides a dynamic, geospatial representation of the airfield, with colour‑coded icons indicating the status of each circuit and fixture. Operators can click on any element to view detailed status, historical data, or to issue commands.
  • Security Management: The server implements role‑based access control (RBAC), allowing different user levels (operator, supervisor, administrator) with different permissions. All user actions are logged for audit purposes. The server also supports encrypted communication (TLS/SSL) to protect against unauthorised access and eavesdropping.

The server is typically deployed in a client‑server architecture, with multiple workstations connecting to the server over the airfield network. In larger airports, a redundant server configuration is used, with a primary server and a hot‑standby backup server that automatically takes over in the event of a failure. The server also includes comprehensive diagnostics and self‑monitoring capabilities, alerting operators if the server itself experiences any issues.

Architecture

System Architecture & Control Logic

The ALCMS server sits at the centre of the control hierarchy, one level above the field controllers and one level below the operator. Upstream, it exchanges real-time status and receives validated commands from PLCs, Remote I/O units, and CCRs, typically reaching them through an Ethernet switch and, where legacy or serial field devices are involved, a Communication Gateway or SCADA Interface performing protocol translation (Modbus, IEC 61850, OPC UA). Downstream, it serves one or more ALCMS Workstations (and Touchscreen HMIs at local panels), pushing map-based status updates and accepting operator commands after validating them against permissions and interlock conditions. Every status change and command is timestamped and written to the historian database, so the server is also the single point where the full operational picture and audit trail come together.

Construction

Physical Construction

The server is built in a standard 19-inch rack-mount chassis, either 2U or 4U depending on storage and expansion needs, with a steel or aluminium enclosure designed for continuous airflow through front-to-rear cooling fans. Dual hot-swappable power supplies sit in the rear, each independently fed from the facility's redundant UPS circuits so either can fail without interrupting operation, and hot-swap drive bays at the front allow RAID array members to be replaced without powering down the server. Internal cabling and expansion cards (network interfaces, serial adapters, fibre SFP modules) are secured to the chassis rail system per rack-mount convention, and the unit is designed to sit in a temperature- and humidity-controlled equipment room or server rack rather than an outdoor cabinet. Front-panel status LEDs and a local console port allow basic diagnostics without needing to log in remotely, and the chassis is typically secured in the rack with a lockable front bezel to prevent unauthorised access to drive bays and power switches.

Field Notes

Common Field Issues

Hardware Failure

Like all servers, the ALCMS server is subject to hardware failures—power supply failure, hard disk failure, or motherboard issues. Always deploy a redundant server configuration (active‑standby) and keep spare parts on hand. Implement regular hardware health checks and monitoring.

Network Connectivity Issues

If the server loses network connectivity to field equipment, it cannot control or monitor the AGL system. Use redundant network paths (dual‑homed servers) and monitor network health. Implement automatic failover to backup network interfaces.

Software Bugs and Updates

ALCMS software can contain bugs that affect performance or reliability. Ensure that the software is properly tested before deployment, and apply patches and updates in a controlled manner. Maintain a fallback version (snapshot or backup) to roll back if needed.

Database Corruption

The real‑time and historian databases can become corrupted due to power loss or software errors. Use a robust database management system (DBMS) with transaction logging, and perform regular backups. Consider using a database replication feature to maintain a copy on the backup server.

Cybersecurity Threats

The ALCMS server is a potential target for cyberattacks. Implement strong access controls, use encrypted communication, regularly update antivirus and security patches, and monitor for unusual activity. Conduct regular security audits and penetration tests.

Time Synchronisation Issues

If the server's clock is not synchronised with field equipment, time‑stamped events (alarms, logs) will be inconsistent. Use a Network Time Protocol (NTP) server to synchronise the system clock across all devices.

Inadequate Cooling and Power

Servers generate significant heat and require clean, stable power. Install the server in a temperature‑controlled equipment room with adequate ventilation and cooling. Use a UPS to protect against power surges and provide backup power during short outages.

Diagnostics

Troubleshooting Guide

Active Server Fails Over to Standby Unexpectedly
Likely Cause
A hardware fault (power supply, disk, or motherboard) on the active server triggered the redundant active-standby configuration to fail over, or the failover was triggered by a network connectivity loss rather than a genuine hardware fault.
Diagnostic Steps
Check the failed-over server's hardware health logs for the fault that triggered failover; verify network connectivity to field equipment was intact at the time of the event to rule out a network-triggered failover.
Corrective Action
Replace the faulted hardware component using spares on hand; once repaired, restore it as standby rather than immediately failing back, to confirm stability first.
Server Cannot Control or Monitor Field Equipment
Likely Cause
Loss of network connectivity between the server and field equipment, either on the primary network path or, if redundant dual-homed paths are fitted, a failure of automatic failover to the backup interface.
Diagnostic Steps
Check network health monitoring for the affected path; confirm whether the automatic failover to the backup network interface actually engaged; test connectivity on both primary and backup paths independently.
Corrective Action
Restore the failed network path; repair the automatic failover mechanism if it did not engage as designed, and re-test failover behaviour before considering the fault closed.
System Behaves Unexpectedly After a Recent Software Update
Likely Cause
A bug introduced in the recent patch or update, applied without adequate pre-deployment testing.
Diagnostic Steps
Correlate the onset of the unexpected behaviour with the update timeline; check release notes for known issues in the applied version.
Corrective Action
Roll back to the maintained fallback version (snapshot or backup) if the bug is confirmed; escalate to the software vendor and re-test thoroughly before reapplying the update in a controlled window.
Historical Data Missing, Corrupted, or Inconsistent
Likely Cause
Real-time or historian database corruption caused by an unexpected power loss or a software error during a write operation.
Diagnostic Steps
Check database transaction logs for errors around the time the corruption is first noticed; confirm whether a power event coincided with the issue; check the status of database replication to the backup server.
Corrective Action
Restore from the most recent verified backup or replicated copy on the backup server; investigate and correct the underlying cause (power protection, software fix) to prevent recurrence.
Alarm and Log Timestamps Don't Match Across Devices
Likely Cause
The server's clock has drifted out of synchronisation with field equipment, most likely due to an NTP server fault or a device that has stopped syncing to it.
Diagnostic Steps
Check NTP server status and reachability from the ALCMS server and affected field devices; compare current system clock against a reliable time source to quantify the drift.
Corrective Action
Restore NTP synchronisation for the affected device(s); if the NTP server itself has failed, repair or replace it and re-verify synchronisation across all connected devices.
Server Performance Degrading or Unexpected Shutdowns
Likely Cause
Inadequate cooling or ventilation in the equipment room causing thermal throttling or protective shutdown, or an unstable power supply triggering resets.
Diagnostic Steps
Check equipment room temperature against the server's rated operating range; review UPS logs for power events coinciding with the performance issue or shutdowns.
Corrective Action
Restore proper ventilation/cooling in the equipment room; repair or upsize the UPS if power instability is confirmed as the trigger.

Precautions

Safety & Operational Notes

Isolate Both Redundant Power Supplies
Electrical Safety

The server's redundant, hot-swappable power supplies are designed to keep it running through a single-input failure; before internal work, isolate and lock out both inputs independently and verify zero energy, since disconnecting only one leaves the unit live.

UPS-Backed Output May Stay Live
Electrical Safety

Where the server's supply is UPS-backed, isolating the mains feed to the UPS does not necessarily de-energise the server; confirm the UPS output itself is isolated or the server is cleanly shut down before disconnecting power cabling.

ESD-Sensitive Electronics
Operational

Use anti-static precautions when handling internal boards, drives, or memory modules.

Data Integrity Before Shutdown
Operational

Perform an orderly shutdown of the ALCMS software and confirm any active database transactions or logs are safely committed before removing power, to avoid corrupting the airfield's historical lighting/fault records.

Access Control for Configuration Changes
Compliance

Make configuration or software changes only under an authorised change-control process, since the server is the central point of control for CCRs, remote I/O, and smart fixtures across the airfield.

Restore to Compliant State
Compliance

Confirm the server re-establishes communication with all connected field devices and that alarm/logging functions are operating correctly before closing out the work.

Field Insight

Engineering & Expert Notes

RS
By Rahul Sharma
Airfield Ground Lighting Specialist
Test Failover on a Schedule, Not Just at Commissioning
Reliability

A hot-standby server pair that failed over perfectly at commissioning can silently lose that capability months later if the standby's software drifts out of sync with the primary through unmirrored patches or config changes. Run a real, scheduled failover test rather than trusting a "standby healthy" status light, since the status check itself may not exercise the actual cutover logic.

Verify Backups Restore, Not Just Complete
Data Integrity

A backup job that reports success only confirms the write completed, not that the resulting file is a usable database. Periodically perform an actual restore-and-verify onto a test instance; a corrupted backup that's gone unnoticed for months is far worse than no backup, because it creates false confidence.

Time Sync Faults Look Like Data Faults
Troubleshooting

When the server's time reference drifts, alarm sequences and event logs can appear to arrive out of order or duplicate, which technicians often misdiagnose as a field-device or database problem. Check NTP/time-sync health early in any troubleshooting sequence involving odd event ordering, before chasing the field layer.

Patch Management Needs a Rollback Plan, Not Just a Schedule
Cybersecurity

Applying security patches to a live ALCMS server without a tested rollback path risks trading a theoretical vulnerability for an actual outage if a patch conflicts with the control software. Always validate patches on a non-production instance first and keep a known-good snapshot ready before touching the production server.

Watch Log Growth as a Leading Indicator
Capacity Planning

Steadily rising event-log or database growth often signals a chattering field device (a fixture or CCR flapping between states) well before that device causes a visible operational problem. Trend storage consumption over time and investigate the source of any unexplained increase rather than simply expanding storage capacity.

Dual-Homed Doesn't Mean Automatically Redundant
Networking

A server with two network interfaces only gains real redundancy if both paths actually terminate on physically independent switches and, ideally, separate power feeds; two NICs cabled into the same switch just moves the single point of failure one hop downstream. Verify the physical diversity of both paths during design review, not just the server's NIC count.

Typical maintenance tasks and intervals are: Hardware Health Check (monthly); Failover / Redundancy Test (quarterly); Database Backup & Integrity Check (weekly); Security Patch & Antivirus Update (monthly); Time Synchronisation Verification (quarterly); UPS & Cooling Inspection (semi-annual); Software & Firmware Review (quarterly); Log & Storage Capacity Review (monthly). Your airport's approved maintenance programme takes precedence.

Q9How do I troubleshoot common ALCMS Server faults?

Common symptoms covered are: Active Server Fails Over to Standby Unexpectedly; Server Cannot Control or Monitor Field Equipment; System Behaves Unexpectedly After a Recent Software Update; Historical Data Missing, Corrupted, or Inconsistent; Alarm and Log Timestamps Don't Match Across Devices; Server Performance Degrading or Unexpected Shutdowns. For example, for "Active Server Fails Over to Standby Unexpectedly": Likely Cause: A hardware fault (power supply, disk, or motherboard) on the active server triggered the redundant active-standby configuration to fail over, or the failover was triggered by a network connectivity loss rather than a genuine hardware fault. Diagnostic Steps: Check the failed-over server's hardware health logs for the fault that triggered failover; verify network connectivity to field equipment was intact at the time of the event to rule out a network-triggered failover. Corrective Action: Replace the faulted hardware component using spares on hand; once repaired, restore it as standby rather than immediately failing back, to confirm stability first.
