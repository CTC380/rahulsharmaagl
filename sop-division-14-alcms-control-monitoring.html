SOP-281 ALCMS Start-Up
Purpose

To establish a controlled procedure for starting the ALCMS and verifying that the system is ready for operational control and monitoring.

Pre-Start Verification

Verify:

  • ALCMS workstation/server availability.
  • UPS/power supply.
  • Network availability.
  • PLC status.
  • HMI availability.
  • Communication with CCRs.
  • Communication with field equipment.
  • Time synchronization.
  • Alarm system status.
  • Database availability.
  • No active maintenance lockout affecting operation.
Procedure
  1. Confirm authorization to start the ALCMS.
  2. Verify control room power.
  3. Energize approved ALCMS equipment.
  4. Start servers/workstations according to site sequence.
  5. Launch HMI/SCADA application.
  6. Log in using authorized credentials.
  7. Verify system health.
  8. Check communication status.
  9. Check PLC status.
  10. Check CCR availability.
  11. Review active alarms.
  12. Verify date/time.
  13. Confirm correct operational mode.
  14. Verify system is ready for control.
Acceptance

ALCMS shall not be released for operational control until critical communication, control and monitoring functions are confirmed.

SOP-282 ALCMS Shutdown

Critical Rule — Do not assume that shutting down an ALCMS workstation automatically switches the airfield lighting to a safe operational state. Verify the actual control architecture.

Purpose

To safely shut down ALCMS equipment without unintentionally affecting required airfield lighting operations.

Procedure
  1. Confirm shutdown authorization.
  2. Coordinate with Airport Operations/ATC as applicable.
  3. Confirm current lighting configuration.
  4. Verify no critical operation depends on the workstation being shut down.
  5. Save required records.
  6. Confirm active alarms.
  7. Place control system in approved shutdown/standby condition.
  8. Exit HMI/SCADA application.
  9. Shut down workstation/server according to approved sequence.
  10. Maintain required monitoring/control redundancy.
  11. Record shutdown.

SOP-284 CCR Remote Control

Critical Principle — Command → CCR response → Lighting response → ALCMS feedback must be verified.

Purpose

To establish a controlled procedure for remotely controlling CCRs through ALCMS.

Procedure
  1. Confirm correct CCR identification.
  2. Verify communication status.
  3. Confirm CCR is available for remote operation.
  4. Verify no maintenance lockout.
  5. Confirm operational authorization.
  6. Select required CCR.
  7. Confirm safety-critical commands (e.g. stop bars, runway guard/status lights, taxiway route lighting) follow the approved ATC / A-SMGCS interlock logic.
  8. Issue approved command.
  9. Verify command acknowledgement.
  10. Verify actual CCR status.
  11. Verify output/current indication where available.
  12. Confirm corresponding lighting response.
  13. Record command/event.
SOP-285 Brightness Control
Purpose

To establish controlled selection of AGL lighting intensity through ALCMS.

Procedure
  1. Identify required lighting circuit.
  2. Confirm operational requirement.
  3. Select approved intensity level.
  4. Issue brightness command.
  5. Verify CCR response.
  6. Verify actual status.
  7. Verify lighting response.
  8. Monitor for alarms.
  9. Record significant operational changes.
Control

Brightness settings shall be based on the approved airport operational philosophy and applicable aerodrome requirements.

Major

Advisory

SOP-288 Alarm Acknowledgement

Important — Acknowledging an alarm does not mean the fault has been cleared.

Purpose

To ensure alarms are acknowledged without masking the underlying fault.

Procedure
  1. Identify alarm.
  2. Read alarm description.
  3. Check affected equipment.
  4. Assess operational significance.
  5. Acknowledge alarm.
  6. Record response where required.
  7. Initiate troubleshooting.
SOP-289 Alarm Reset

Critical Rule — Do not repeatedly reset a recurring alarm without investigating its cause.

Purpose

To establish controlled resetting of ALCMS alarms.

Procedure

  2. Determine root condition.
  3. Confirm corrective action.
  4. Verify equipment is safe.
  5. Reset alarm using approved command.
  6. Verify alarm clears.
  7. Confirm equipment returns to normal.
  8. Check event log.
  9. Record reset where required.

SOP-297 Remote Equipment Status Verification

Golden Test — HMI indication ≈ PLC status ≈ CCR status ≈ actual equipment condition within the defined system architecture.

Purpose

To verify that ALCMS status information corresponds to the actual field equipment.

Procedure

  2. Note displayed status.
  3. Verify field equipment status using approved independent indication where available.
  4. Compare commanded status, actual status and feedback status.
  5. Identify discrepancies.
  6. Investigate communication/control faults.
  7. Record results.

Division-Wide Requirements

The master control workflow, alarm management workflow, quality hold points, common failure modes and master checklist that apply across all 20 Division 14 procedures.

A. Master Control Workflow

The following sequence should be applied for every ALCMS control action:

USER LOGIN SYSTEM HEALTH CHECK PLC/NETWORK/CCR COMM CHECK EQUIPMENT STATUS VERIFICATION ALARM REVIEW AUTHORIZED CCR COMMAND BRIGHTNESS COMMAND CCR RESPONSE FIELD LIGHTING RESPONSE ALCMS FEEDBACK EVENT RECORDING DATA LOGGING OPERATIONAL MONITORING

B. Alarm Management Workflow

The following sequence should be applied for every alarm:

ALARM GENERATED IDENTIFY EQUIPMENT CHECK ALARM PRIORITY ASSESS OPERATIONAL IMPACT ACKNOWLEDGE ALARM INVESTIGATE ROOT CONDITION CORRECT FAULT RESET ALARM VERIFY NORMAL STATUS REVIEW EVENT LOG CLOSE ALARM

Important distinction: Alarm Acknowledged ≠ Alarm Cleared ≠ Fault Repaired. These are three different conditions and should remain clearly distinguishable in the ALCMS.

C. Quality Hold Points

  • HP-01 — User AccessVerify authorized user and correct access level.
  • HP-02 — System HealthVerify servers, HMI, PLC and network.
  • HP-03 — CommunicationVerify communication with critical field equipment.
  • HP-04 — CCR ControlVerify remote command and actual response.
  • HP-05 — BrightnessVerify selected intensity and actual output.
  • HP-06 — AlarmVerify alarm generation and indication.
  • HP-07 — Event LogVerify command and fault events are recorded.
  • HP-08 — Data LogVerify required operational data is being stored.
  • HP-09 — ConfigurationVerify approved configuration revision.
  • HP-10 — BackupVerify current recoverable backup.
  • HP-11 — Functional TestVerify end-to-end system operation.
  • HP-12 — Final ReleaseRelease ALCMS only after all critical test results are satisfactory.

D. Common ALCMS Failure Modes

  • 1. HMI Shows CCR OFF but CCR Is ONPossible causes: communication failure, incorrect feedback, PLC mapping error, database/status issue.
  • 2. HMI Command Does Not Operate CCRCheck:
    USER PERMISSIONREMOTE MODECOMMUNICATIONPLCCCR CONTROLINTERLOCK
  • 3. Alarm Appears RepeatedlyDo not repeatedly acknowledge/reset. Investigate the underlying equipment fault.
  • 4. Alarm Not AppearingPossible causes: sensor/input failure, PLC logic issue, communication problem, incorrect alarm configuration.
  • 5. Event Timestamp IncorrectCheck: system clock, time synchronization, server time, PLC time, HMI/database time.
  • 6. Equipment OfflineCheck:
    POWERPHYSICAL LINKNETWORKCONTROLLERCOMMUNICATIONDEVICE
  • 7. Brightness Command IncorrectCheck: user command, HMI mapping, PLC logic, CCR configuration, actual CCR response.
  • 8. Data Missing From LogCheck: logging service, database, storage capacity, communication, time synchronization.
  • 9. Configuration Changed Without RecordTreat as a configuration-control issue and establish the approved baseline before further modification.
  • 10. Backup Cannot Be RestoredA backup/recovery failure should be treated as a serious system reliability issue and investigated immediately.

Division 14 — ALCMS Golden Rule

“Never trust a control command merely because the HMI accepted it. A reliable ALCMS must prove the complete chain: authorized command → communication → PLC/control logic → CCR response → actual AGL equipment response → feedback → alarm/event recording. The displayed status must represent the actual field condition.”

Division 14 — SOP Approval Principle

Each project should adapt these SOPs to its own approved ALCMS architecture, control philosophy, cause-and-effect matrix, HMI/SCADA design, PLC logic, network architecture, cybersecurity requirements and CCR manufacturer's documentation.

Approved control philosophy, cybersecurity policy and manufacturer's instructions shall take precedence wherever they impose more restrictive requirements.

Frequently Asked Questions

Quick answers about ALCMS / Control & Monitoring SOPs in the AGL SOP Library.

Q1What is Division 14 — ALCMS / Control & Monitoring SOPs?

Division 14 is a set of 20 procedures (SOP-281 to SOP-300, Rev 0) for the Airfield Lighting Control & Monitoring System. It covers start-up, shutdown, user access, CCR remote control, brightness control, status and alarm monitoring, event and data logging, PLC/HMI operation, network communication, backup, configuration management and functional testing.

Q2What governs command permissions and alarm priorities?

The approved control philosophy, cause-and-effect matrix, HMI/SCADA design, PLC logic, network architecture, cybersecurity requirements, CCR manufacturer's documentation and airport operational procedures. Command permissions, alarm priorities, reset logic, communication protocols and backup procedures are site-specific.

Q3Does acknowledging an alarm mean the fault is cleared?

No. Alarm Acknowledged is not the same as Alarm Cleared, which is not the same as Fault Repaired, and the ALCMS should keep these three conditions clearly distinguishable (SOP-288). Acknowledge without masking the underlying fault, then initiate troubleshooting.

Q4Can a recurring alarm simply be reset?

No. Do not repeatedly reset a recurring alarm without investigating its cause (SOP-289). Identify the root condition, confirm corrective action, verify the equipment is safe, reset using the approved command, and confirm the alarm clears and the equipment returns to normal.

Q5What is the alarm management workflow?

Alarm generated, identify equipment, check priority, assess operational impact, acknowledge, investigate the root condition, correct the fault, reset, verify normal status, review the event log and close the alarm.

Q6What are the rules for ALCMS user access?

Use individually assigned credentials, confirm your user identity and role, do not share credentials or use another person's account, do not write passwords on the console, do not bypass access control, lock or log out when leaving the workstation, and report suspected unauthorized access (SOP-283).

Q7When is an ALCMS backup considered successful?

Not merely because a file was created. Integrity and recoverability must be verified per the approved recovery procedure (SOP-298). Backups may include the PLC program, HMI application, ALCMS, alarm, user and network configuration, and the database, and each is labeled with date, system version and configuration revision.

Q8What is the master ALCMS control workflow?

User login, system health check, PLC/network/CCR communication check, equipment status verification, alarm review, authorized CCR command, brightness command, then observing CCR response, field lighting response and ALCMS feedback, followed by event recording, data logging and operational monitoring.
