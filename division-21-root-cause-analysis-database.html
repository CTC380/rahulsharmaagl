Initial Issue

Core logic — Failure → Evidence → Cause → Root Cause → Corrective Action → Verification → Prevention. One failure can have multiple contributing factors but should ultimately have a technically verified root cause wherever sufficient evidence exists.

Diagnostic principle — Do not stop at "what failed?" Establish "why did it fail?", verify the answer with objective evidence, eliminate the cause, and prove that the corrective action prevented recurrence. Recording "Root Cause: LED driver failure" only restates what failed — it is not a root cause.

RC-11 Component Root Cause
Definition

A specific component is established as the primary source of failure.

Examples
  • Failed LED driver
  • Failed transformer winding
  • Failed connector
  • Failed sensor
  • Failed CCR component
Important Distinction

Component failure describes what failed. Component root cause means the investigation has established that the component itself was the primary causal source.

RC-12 Human Root Cause
Definition

Human action, error, decision or omission is established as a contributing or primary cause.

Examples
  • Incorrect connection
  • Incorrect setting
  • Incorrect component selection
  • Failure to follow required instruction
  • Incorrect interpretation
Investigation — Consider
  • Competency
  • Training
  • Workload
  • Supervision
  • Human-machine interface
  • Availability of instructions
  • Work conditions
Important Principle

Human root cause should not automatically mean "technician error." The surrounding system conditions should also be examined.

RC-13 Procedural Root Cause
Definition

The applicable procedure itself is missing, inadequate, incorrect, unclear or unsuitable.

Examples

  • Inadequate inspection checklist
  • Incorrect testing procedure

  • Outdated procedure
Important Distinction

Human root cause: person did not correctly perform the required process. Procedural root cause: the process/instruction itself was inadequate or unavailable.

RC-18 Unknown / Pending Root Cause
Definition

The root cause cannot yet be established with sufficient evidence. This category is important because the database should not force a false root cause. Use "Unknown/Pending" when investigation is still underway.

Required Follow-Up
  • Evidence collection
  • Additional testing
  • Component examination
  • Manufacturer investigation
  • Failure history review
  • RCA review
Principle

Once sufficient evidence is obtained, update the RCA classification. Never force-fit a root cause the evidence does not yet support.

RM-01 5-Why Analysis
Purpose

Used to progressively investigate why the failure occurred.

Example
  • Why did runway light fail? → Driver failed.
  • Why did driver fail? → Excessive thermal stress.
  • Why was thermal stress excessive? → Heat dissipation was inadequate.
  • Why was heat dissipation inadequate? → Installation/thermal interface condition was unsuitable.
  • Why was this not identified? → Required verification was not included/adequately performed.

The final answer must be supported by evidence — not simply the fifth answer.

Best Use
  • Straightforward recurring failures
  • Maintenance failures
  • Installation failures
  • Process failures
RM-02 Fishbone Analysis
Purpose

Also known as Ishikawa/cause-and-effect analysis. Used to identify possible causes across multiple categories.

Typical AGL Branches
ElectricalMechanicalOpticalThermalEnvironmentalInstallationMaintenanceHumanProcedureMaterialEquipmentDocumentation
Best Use

When several potential causes exist and the team needs to systematically organize them before verification.

RM-03 Fault-Tree Analysis
Purpose

Works from the top-level failure downward to possible causal events.

Example

Runway lighting outage → OR:

  • CCR failure
  • Primary cable failure
  • Transformer failure
  • Fixture failure
  • Control failure

Then each branch can be further decomposed.

Best Use
  • Critical lighting
  • Multiple circuit failures
  • System outages
  • Control failures
  • Safety-critical systems

Purpose

Reconstructs the sequence of events before, during and after the failure.

Example

RM-07 Contributing-Factor Analysis
Purpose

Identifies factors that did not independently cause the failure but increased its likelihood or severity.

Example

Primary root cause: connector defect

Contributing factors:

  • Moisture
  • High temperature
  • Poor maintenance
  • Inadequate inspection
Recommended Structure

Root Cause + Contributing Factors + Failure Mechanism = Complete RCA

RM-08 Root-Cause Verification
Purpose

Confirms that the proposed root cause actually explains the failure.

Verification Methods
  • Repeat testing
  • Controlled replacement
  • Laboratory examination
  • Failure reproduction
  • Component teardown
  • Manufacturer analysis
  • Comparison with healthy equipment
  • Historical data
Critical Question

If the identified root cause is removed, does the failure mechanism disappear or materially reduce? If not, the RCA may be incomplete or incorrect.

RM-09 Corrective-Action Verification
Purpose

Confirms that corrective action has actually eliminated or controlled the root cause.

Sequence
ROOT CAUSE IDENTIFIEDCORRECTIVE ACTIONIMPLEMENTATIONTESTINGOPERATIONAL MONITORINGFAILURE RECURRENCE REVIEWEFFECTIVENESS CONFIRMED
Example

Repeated connector failures caused by a sealing problem — Corrective action: improved sealing method → Verification: inspection + test → Monitoring: subsequent failure trend → Effectiveness: no recurrence over defined monitoring period.

Division-Wide Requirements

Master workflow, data structure, status classification, RCA quality levels and cross-division linkage that apply across all 27 Division 21 root-cause and RCA-method topics.

A. RCA Master Workflow

Every Division 21 case should progress through the following twelve-step workflow, from identification through to lessons learned:

1. FAILURE IDENTIFICATION2. FAILURE CLASSIFICATION3. IMMEDIATE CAUSE4. FAILURE MECHANISM5. CONTRIBUTING FACTORS6. ROOT CAUSE
7. RCA METHOD8. ROOT-CAUSE VERIFICATION9. CORRECTIVE ACTION10. CORRECTIVE-ACTION VERIFICATION11. PREVENTIVE ACTION12. LESSONS LEARNED

Lessons learned should feed back into SOPs, inspection checklists, maintenance plans, the Product Encyclopedia, training, design/specification and supplier evaluation.

B. Root Cause vs. Immediate Cause vs. Contributing Factor

This distinction is mandatory in the database — recording only the immediate cause is not an acceptable substitute for a root cause.

Example — Runway Edge Light Failure

Failure: Runway edge light failed.

Immediate cause: LED driver failed.

Failure mechanism: Driver electronics overheated and failed.

Contributing factors: High ambient temperature; restricted heat dissipation.

Root cause: Product thermal design weakness.

Corrective action: Driver/product design improvement.

Verification: Monitor modified units for recurrence.

This structure is far stronger than simply recording "Root Cause: LED driver failure", because that only describes what failed, not why it failed.

D. RCA Quality / Confidence Level

Level 1 — Suspected: evidence suggests a possible cause but is insufficient

Level 2 — Probable: multiple pieces of evidence support the cause

Level 3 — Verified: testing/inspection/evidence confirms the cause

Level 4 — Demonstrated: the failure mechanism has been reproduced or conclusively established

Particularly useful for tracking confidence on Unknown/Pending Root Cause cases as evidence accumulates.

Division 21 vs. Divisions 01–20

Divisions 01–20 classify what failed and where the failure occurred. Division 21 determines why the failure occurred, how the cause was established, and whether the corrective action actually eliminated the cause. It should never be used to force a root cause where evidence is insufficient — the Unknown/Pending category and the RCA confidence levels exist precisely to keep the database evidence-based rather than assumption-based, while still tracking every case through to a verified, closed corrective action.

Frequently Asked Questions

Quick answers about root cause analysis in the AGL Failure Database, as covered in Division 21.

Q1What is Division 21 — Root Cause Analysis Database in the AGL Failure Database?

Division 21 is the analytical backbone of the database. It contains 27 published topics: 18 root-cause categories (RC-01 to RC-18) and 9 RCA methods (RM-01 to RM-09). It establishes why every failure occurred, how the cause was verified and whether corrective action eliminated it.

Q2What are the 18 root-cause categories?

Electrical, mechanical, optical, thermal, environmental, installation, maintenance, design, manufacturing, material, component, human, procedural, documentation, software, communication and operational root causes, plus an Unknown / Pending root-cause category.

Q3What are the 9 RCA methods?

5-Why analysis, fishbone analysis, fault-tree analysis, failure-mode analysis, evidence analysis, timeline reconstruction, contributing-factor analysis, root-cause verification and corrective-action verification.

Q4What is the difference between a root cause, an immediate cause and a contributing factor?

The distinction is mandatory: recording only the immediate cause is not an acceptable substitute for a root cause. For a runway edge light failure, the immediate cause is that the LED driver failed, the mechanism is driver electronics overheating, the contributing factors are high ambient temperature and restricted heat dissipation, and the root cause is a product thermal design weakness. Recording “LED driver failure” alone only describes what failed, not why.

Q5What workflow does every RCA case follow?

Every case progresses through twelve steps: failure identification, failure classification, immediate cause, failure mechanism, contributing factors, root cause, RCA method, root-cause verification, corrective action, corrective-action verification, preventive action and lessons learned. Lessons learned should feed back into SOPs, inspections and related documents.

Q6How is RCA status and confidence tracked?

Status runs from Open through Under Investigation, Cause Suspected, Cause Identified, Verification Pending, Corrective Action Open and Effectiveness Pending to Closed, with Reopened used when the failure recurred or the RCA proved inadequate. Confidence has four levels: Suspected, Probable, Verified and Demonstrated, which is useful for tracking Unknown/Pending cases as evidence accumulates.

Q7What if the evidence does not support a root cause?

Division 21 should never be used to force a root cause where evidence is insufficient. The Unknown/Pending category and the RCA confidence levels exist to keep the database evidence-based rather than assumption-based.

Q8How does Division 21 relate to Divisions 01–20?

Divisions 01–20 classify what failed and where. Division 21 determines why it failed, how the cause was established and whether corrective action eliminated it. One failure can carry several linked classifications without duplicating the failure record.
