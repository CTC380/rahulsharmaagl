AGL-CS-097 — Local Control Works but Remote Control Fails

The AGL Knowledge Hub | Engineering Case Study Series. A control-system investigation where an incorrectly configured remote-authorization signal prevented remote operation — from local verification through PLC logic analysis, authorization testing, and configuration correction.

Case ID

AGL-CS-097

Category

ALCMS Remote Control Diagnostics, PLC Control Logic & Airport Automation Systems

Level

Expert

Case Type

Engineering Simulation

Primary Skill

Investigation of a control-system failure where local equipment operation is normal but remote control from the ALCMS fails

Important: This is an engineering simulation created for training. It is not presented as an actual airport incident. All readings, values, dates and outcomes are illustrative, and no airport, organisation, person or manufacturer is identified or implied.

1Case Study Overview

During routine evening operations, the airport operations center reported that Taxiway Circuit TW-7 could not be switched ON from the ALCMS workstation.

Operators observed:

  • Remote ON command failed.
  • Remote OFF command failed.
  • Brightness changes failed.
  • ALCMS communication appeared healthy.
  • No major communication alarms were active.

However, field inspection confirmed that:

  • Local control-panel operation was normal.
  • Circuit energized correctly locally.
  • CCR output was normal.
  • Field lights operated correctly.

Because local operation remained fully functional while remote operation failed, a detailed investigation was initiated covering remote/local selection, PLC control logic, command processing, control-permission logic, interlocks, communication verification, control relays, and command acknowledgment.

The investigation identified a control-permission logic lockout caused by an incorrectly configured remote-control authorization signal, preventing PLC remote commands from reaching the field control circuit.

This case demonstrates that local operation confirms equipment health, while remote-control failure usually indicates a problem in the automation control path, authorization logic, or control interface.

A typical remote-control architecture includes:

  • ALCMS workstation.
  • SCADA server.
  • PLC controller.
  • Communication network.
  • Remote-control authorization logic.
  • Interlock logic.
  • Output relays.
  • Local/remote selector.
  • Field control panel.
  • Lighting circuit.

Remote-control failures may result from:

  • Authorization logic errors.
  • Local/remote selector problems.
  • PLC output failures.
  • Interlock activation.
  • Control relay failures.
  • Command-processing errors.
  • Configuration errors.
  • Software modifications.

Remote operation requires both communication and control authorization.

7Control-Path Principle

Remote command → ALCMS → PLC processing → Authorization logic → Interlock verification → Output relay → Field control circuit → Lighting operation
Authorization blocked → Remote command rejected → Local control unaffected → Remote operation unavailable

Local operation bypasses part of the remote control path.

Testing confirmed:

Circuit energization Normal

Step 2: Verify Communication

Communication testing showed:

  • PLC communication healthy.
  • ALCMS connected.
  • Status updates normal.
  • No communication errors.

Communication was healthy.

Step 3: Verify Command Transmission

ALCMS event logs showed:

  • Command transmitted.
  • PLC received command.
  • Command processed.
  • No output activation occurred.

The PLC received the remote command.

Step 4: PLC Logic Analysis

PLC monitoring showed:

Remote command bit: ON

Output command bit: OFF

Authorization bit: OFF

The authorization logic blocked the command.

Step 5: Authorization Logic Verification

Logic analysis identified:

Remote output permitted only when:

  • Remote authorization active.
  • Maintenance lockout inactive.
  • Emergency interlock clear.
  • Local override disabled.

The remote authorization signal was inactive.

Step 6: Authorization Input Test

Input testing showed:

Remote authorization input: OFF

Expected: ON

The authorization signal was missing.

Step 7: Configuration Review

Investigation revealed:

  • Recent software modification.
  • Incorrect remote-permission mapping.
  • Authorization signal assigned to the wrong input address.

The PLC configuration was incorrect.

10Root Cause

Training-Case Finding

Remote control failed because of incorrect PLC remote-control authorization logic configuration, resulting in:

  • Remote command rejection.
  • Output inhibition.
  • Failure of remote control.
  • Normal local operation.

Communication and field equipment remained healthy.

The primary failure mechanism was control-permission logic misconfiguration.

11Corrective Action

The engineering team:

  1. Corrected PLC authorization mapping.
  2. Verified input addressing.
  3. Tested authorization logic.
  4. Verified interlock operation.
  5. Tested remote ON/OFF commands.
  6. Tested brightness control.
  7. Verified command acknowledgment.
  8. Updated software documentation.
  9. Implemented configuration validation.
  10. Performed full remote-control testing.

16Engineer's Decision Point

You observe: Local control works. Remote control fails. Communication healthy. Field equipment operational. What should you investigate first?

A. Replace the CCR.
B. Replace the communication network.
C. Verify command transmission, analyze PLC logic, check authorization signals, test interlocks, verify output relays, and validate remote-control configuration.
D. Replace the lighting circuit.
Correct answer: C. Local operation normal with communication healthy points to a control-path or authorization problem. Systematic verification of command transmission, PLC logic, authorization signals, interlocks, output relays, and configuration will identify the cause without unnecessary equipment replacement.

19Frequently Asked Questions

Quick answers about remote control failure and PLC authorization logic.

Q1What is AGL-CS-097?

AGL-CS-097 is an engineering training case study. It covers a taxiway circuit that worked locally but could not be switched from the ALCMS because of a control-permission lockout. It is an engineering simulation created for training, not a report of an actual airport incident.

Q2What does it mean when local control works but remote fails?

Local operation confirms the equipment is healthy. Remote failure points to the automation control path, authorization logic or control interface.

Q3How did the command flow in AGL-CS-097?

The ALCMS transmitted the command and the PLC received and processed it, but no output activated. The remote command bit was ON while the output command bit and authorization bit were OFF.

Q4What does the PLC require before it permits a remote output?

Remote authorization active, maintenance lockout inactive, emergency interlock clear and local override disabled. The remote authorization input was OFF when it should have been ON.

Q5Was communication or the field equipment at fault?

No. PLC communication was healthy, the ALCMS was connected, status updates were normal and the CCR and lights worked locally.

Q6What was the root cause of AGL-CS-097?

Incorrect PLC remote-control authorization logic configuration, caused by a recent software modification with incorrect remote-permission mapping. This inhibited outputs and rejected remote commands.

Q7How was it corrected?

The team corrected the PLC authorization mapping and verified input addressing, authorization logic and interlock operation. They tested remote ON/OFF and brightness control, verified command acknowledgment, updated software documentation, implemented configuration validation and performed full remote-control testing.

Q8How does this differ from AGL-CS-092?

In 092 a physical interface relay failed. Here the hardware was fine and the PLC logic itself blocked the command.

Q9What is the key lesson from this case?

After software changes, test the full remote-control path, including permissions and interlocks.

20Case Study Conclusion

Key Engineering Principle

When local control works but remote control fails, the field equipment is usually healthy, and effective diagnosis requires systematic verification of the remote control path, PLC command processing, authorization logic, interlock conditions, output relays, communication integrity, and control-system configuration.

Systematic local verification, communication testing, PLC logic analysis, authorization verification, interlock testing, and post-repair remote-control validation provide a complete engineering methodology for restoring reliable remote airfield lighting control and maintaining airport automation integrity.

In AGL engineering, the most valuable diagnostic clue is often the fact that the equipment responds perfectly to local control, because that immediately tells the engineer where not to look and where the real control-system problem is likely to exist.
